# دليل الإصدارات والتوقيع (Magic RDR Android)

يشرح هذا الدليل كيف تُرقَّم الإصدارات، وكيف يُوقَّع الـ APK، وكيف يُنشر **GitHub Release** تلقائياً (بنسختين: 64-bit و32-bit)، وكيف تتحقق من سلامة أي إصدار.

---

## 1. معلومات الهوية

| البند | القيمة |
|---|---|
| معرّف الحزمة | `com.magicrdr.mobile` (لا يتغير أبداً) |
| المستودع | `Zlatan-RDR/MagicRDR-Android` |
| الحد الأدنى للنظام | Android 10 (API 29) |
| النظام المستهدف | Android 16 (API 36) |
| الإطار | .NET 10 MAUI (`net10.0-android` فقط) |
| ملف الـ Workflow | `.github/workflows/main.yml` |
| الاستضافة | `windows-latest` |

**بصمة شهادة التوقيع الدائمة (SHA-256):**

```
af8bd63ec56ca5feb91d788f3cd4c8a02799be6b49f7036bba4348d627bf3b8b
```

هذه البصمة تظهر في كل إصدار موقّع، وفي `README.md`، وفي ملاحظات كل Release. إن اختلفت فلا تثبّت الـ APK.

---

## 2. النسختان المنشورتان في كل Release

| الملف | المعالجات | لمن؟ |
|---|---|---|
| `MagicRDR-Android-v<الإصدار>.apk` | 64-bit (arm64-v8a، ويضم x86_64 افتراضياً للمحاكيات) | معظم الهواتف الحديثة |
| `MagicRDR-Android-v<الإصدار>-armeabi-v7a.apk` | 32-bit ARM فقط | الهواتف القديمة ذات المعالج 32-bit |

- النسختان من **نفس الكود وفي نفس التشغيل**، ولا يختلف بينهما إلا هدف المعالج (`RuntimeIdentifier=android-arm` للثانية).
- لهما نفس `versionName` و`versionCode`، ونفس مفتاح التوقيع، ولذلك كلتاهما تُحدَّث فوق الأخرى لمن غيّر هاتفه.
- الهواتف الحديثة 64-bit تثبّت النسخة الأولى، فهي الأسرع لها.
- حارس البناء يفشل إن لم تحمل نسخة 32-bit مكتبات `armeabi-v7a`، أو إن حملت `arm64-v8a` أو `x86_64`، أو إن اختلفت شهادتها عن شهادة نسخة 64-bit.

## 3. قاعدة التحديث فوق الإصدار القديم

يقبل أندرويد التحديث فقط إذا تحقق الآتي كله:

1. نفس معرّف الحزمة.
2. نفس مفتاح التوقيع (نفس الشهادة).
3. `versionCode` أعلى من المثبّت.

لذلك لا يجوز تغيير المفتاح ولا المعرّف. فقدان المفتاح يعني أن المستخدمين لن يستطيعوا التحديث إلا بإلغاء التثبيت (مع فقدان بياناتهم).

---

## 4. ترقيم الإصدارات

- **`versionCode`** = عدد **الدقائق** منذ `2026-01-01` بتوقيت UTC. يزداد تلقائياً مع الزمن فلا تحتاج لإدارته، وهو الرقم الذي يقارنه أندرويد عند التحديث.
- **`versionName`** = `APP_VERSION_BASE.<n>`، حيث `APP_VERSION_BASE` قيمته الحالية `1.1`، و`n` هو رقم آخر إصدار منشور من هذه السلسلة زائد واحد (1.1.1 ثم 1.1.2 ثم 1.1.3 ...). البناءات الفاشلة أو الملغاة لا تستهلك رقماً، وحذف عمليات البناء القديمة لا يغيّر شيئاً.
- يُقرأ آخر رقم من وسوم git ومن صفحة الـ Releases معاً، فلا تحذف وسم آخر إصدار ولا تغيّره دون داعٍ.
- لبدء سلسلة جديدة (مثل الانتقال إلى `1.2`) عدّل قيمة `APP_VERSION_BASE` داخل `main.yml`، ويبدأ الترقيم من `1.2.1`.
- أندرويد لا يقارن `versionName`، فلا يضر أن يحمل ملف قديم رقماً يبدو أعلى (مثل 1.2.39 داخل الـ APK الأول).

## 5. مفتاح التوقيع والأسرار

- نوع المفتاح: PKCS12، الاسم المستعار (alias) `magicrdr`، RSA 2048، صلاحية 100 سنة.
- أُنشئ مرة واحدة بواسطة `create-keystore.yml` (وقد حُذف الآن من المستودع).
- أسرار المستودع (Settings ← Secrets and variables ← Actions):
  - `ANDROID_KEYSTORE_BASE64`: ملف المفتاح بصيغة base64.
  - `ANDROID_KEYSTORE_PASSWORD`: كلمة المرور.
- متغير اختياري (Variables): `ANDROID_CERT_SHA256`. إذا ضُبط، يفشل البناء عند اختلاف بصمة الشهادة عنه، وهذا حماية من توقيع بمفتاح خاطئ.
- أعلام `apksigner`: توقيع v1 مغلق، v2 مفتوح، v3 مفتوح. والتحقق يشترط **v3** فقط. ظهور `v2 = False, v3 = True` طبيعي مع minSdk 29.

### تحذيرات المفتاح

- احتفظ **بنسخة احتياطية خارج GitHub** (في مكان آمن ومشفّر) من ملف المفتاح وكلمة المرور.
- لا تضع المفتاح أو كلمة المرور أو ملف base64 داخل المستودع أو في المحادثات أو في سجلات التشغيل.
- `.gitignore` يتجاهل `*.keystore` و`*.jks` و`*.pfx` و`*.p12` و`*.pem` و`*.base64.txt` و`*.apk` و`*.aab` و`*.rpf`، لكن لا تعتمد عليه وحده.
- لا تُعد تشغيل أي Workflow ينشئ مفتاحاً جديداً، فمفتاح جديد = إصدار لا يُحدّث فوق القديم.

## 6. خط النشر (ما يفعله `main.yml`)

الترتيب: فك الـ ZIP (عند الحاجة فقط) ← Commit بـ `[skip ci]` ← حساب الإصدار ← تضمين `names.txt` من الجذر ← تجهيز .NET 10 وJDK 17 ← اختبارات الوحدة (غير مانعة) ← حِمل MAUI ← مكونات Android SDK ← استعادة الحزم ← بناء 64-bit ← **توقيع وتحقق** ← بناء 32-bit (مجلدا `bin` و`obj` يُمسحان قبله) ← **توقيع وتحقق** ← رفع Artifact (14 يوماً) ← **نشر Release**.

### محتوى الـ Release

- الوسم (tag): `v<versionName>` مثل `v1.2.32`.
- العنوان: `Magic RDR <versionName>`.
- الملفان المرفقان: نسخة 64-bit ونسخة 32-bit (روابط تحميل مباشرة عامة بعد جعل المستودع Public).
- ملاحظات الإصدار بالإنجليزية والعربية: قسم "Which file?" يشرح أي ملف لأي هاتف، وخطوات التثبيت، وبصمة SHA-256 لملف كل APK، وبصمة SHA-256 لشهادة التوقيع.
- يُعلَّم الإصدار `--latest`.
- إذا كان الوسم موجوداً مسبقاً: تُستبدل الملفات المرفقة وتُحدَّث الملاحظات.

### متى يُنشر الـ Release؟

- **فقط** عند التوقيع بالمفتاح الدائم (`SIGNED=true`).
- إذا لم توجد الأسرار: يُوقَّع الـ APK بمفتاح تجريبي (debug) ولا يُنشر Release أبداً، حتى لا يصل للمستخدمين ملف لا يمكن تحديثه لاحقاً.

## 7. قائمة الأسماء داخل التطبيق

- ملف `names.txt` في جذر المستودع يُضمَّن في كل Release تلقائياً.
- يُحمَّل عند تشغيل التطبيق في الخلفية، ويظهر عدد الأسماء المعروفة في الشريط.
- التطبيق لا يعيد كتابة القائمة المضمّنة في تخزين الهاتف، ويحفظ فقط الأسماء التي يضيفها المستخدم.

---

## 8. خطوات إصدار جديد

1. عدّل الكود مباشرة داخل المستودع (`src/...`)، كما في `UPDATING.md`.
2. انتظر نجاح التشغيل في Actions.
3. تحقق من ملخص التشغيل: `permanent release key (v2 = False, v3 = True)` للنسختين، ومن الأسطر `Architectures in the 32-bit APK`.
4. تحقق من صفحة Releases: الإصدار الجديد بوسم Latest، وفيه ملفان، والبصمة صحيحة.
5. ثبّت النسخة المناسبة فوق التطبيق القديم على هاتفك وجرّبها.

التعديلات على `**.md` أو `LICENSE` أو `.gitignore` وحدها لا تشغّل بناءً ولا تُنتج Release.

---

## 9. التحقق من أي APK قبل تثبيته

1. قارن بصمة SHA-256 للملف المحمّل بالبصمة المكتوبة في ملاحظات الـ Release للملف نفسه.
2. إن كان لديك Android SDK على جهاز آخر، تحقق من الشهادة بالأمر:

```
apksigner verify --print-certs MagicRDR-Android-v1.2.32.apk
```

وقارن بصمة SHA-256 للشهادة بالبصمة الدائمة في القسم 1.

3. حمّل الـ APK من صفحة Releases الرسمية للمستودع فقط.

## 10. قائمة أمان قبل جعل المستودع Public

- [ ] لا يوجد أي ملف مفتاح (`.keystore` و`.jks` و`.pfx` و`.p12` و`.pem`) ولا `keystore.base64.txt` في الشجرة ولا في السجل التاريخي.
- [ ] الأسرار موجودة فقط في Actions Secrets.
- [ ] حُذف `create-keystore.yml` **وحُذفت تشغيلاته القديمة** (لأنها تحمل Artifact باسم `signing-key-backup` وسجلات).
- [ ] فُتح الـ Commit الذي حذف `create-keystore.yml` وتأكدت أنه لا يحتوي كلمة مرور ولا base64.
- [ ] Settings ← Emails: إبقاء البريد خاصاً وحظر الـ Push الذي يكشفه.
- [ ] Actions ← General: طلب موافقة لتشغيل Workflows القادمة من متعاونين خارجيين (forks).
- [ ] مراجعة ترخيص مشروع Magic-RDR الأصلي (ImFoxxyyy) والتأكد من توافقه مع MIT، وكذلك مصدر قائمة الأسماء `names.txt` (CodeX Games).
- [ ] README و`LICENSE` والـ topics والوصف (About) جاهزة.

بعد التحويل إلى Public: كل ما في السجل التاريخي يصبح عاماً، فراجع README والشارات (badges) وصفحة Releases.

## 11. ملاحظات

- كل Release يُبنى من الكود الموجود في `src` وقت التشغيل.
- كل ملف ZIP يُرفع يبقى في سجل git. بعد الانتقال إلى التعديل المباشر لا حاجة لرفع ZIP.
- توقيع الـ APK يضمن الهوية وإمكانية التحديث، ولا يمنح التطبيق صفة "موثوق" لدى Play Protect.
- التطبيق نسخة أندرويد (Port) مشتقة من Magic-RDR للمطوّر ImFoxxyyy، وغير تابعة لشركة Rockstar Games، ولا يتضمن ملفات اللعبة.
- اختبارات الوحدة تعمل في كل بناء لكنها لا تمنع النشر، فتحقق من نتيجتها في السجل.
